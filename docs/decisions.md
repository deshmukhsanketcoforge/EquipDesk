# Architecture decisions

The decisions behind EquipDesk, one row each: what was chosen, what was rejected and why. This is the decision table from [PLAN.md](../PLAN.md) §3, kept identical to it (`tests/test_evidence_pack.py` fails if they differ). PLAN.md is the source of truth, so change a decision there and copy the row here.

"rev N" refers to earlier revisions of the plan. "Q1" to "Q10" are the design questions the plan answers. "EQP-N" are the tickets that built each part.

| # | Decision | Alternatives rejected | Why / risk handled |
|---|---|---|---|
| D1 | Python 3.12, **FastAPI** backend, official `mcp` SDK (2.x) `MCPServer` (v1's `FastMCP`, renamed in 2.x) mounted via `streamable_http_app()` at `/mcp` | stdio-only server; separate MCP process calling REST | Needed for Swagger + shared logic with minimal moving parts. Risk: mounting the MCP app inside FastAPI requires wiring its session-manager lifespan into FastAPI's lifespan (known gotcha) → spike done in EQP-1 with a trivial `ping` tool, before any business logic. Fallback if blocked: run MCP app as its own uvicorn port in the same image, same service layer. |
| D2 | Logic in **service layer** + repositories; adapters (REST, MCP) are thin | Logic in route/tool functions | Lab: plain-function-first. TDD seam. One behavior, two interfaces, no drift. |
| D3 | Policy tools **deterministic**; LLM only does language (parse item, spot exception claims) | LLM judges policy | Testable/auditable. Spec's `check_request_eligibility(employee_id, item)` has no `reason` arg, so exception claims can't reach it → the **agent** spots them in its Thought step and escalates; tool stays pure. |
| D4 | **Closed, versioned enums** for verdicts and reason codes (see §4) — `StrEnum` in one module `server/codes.py`; Pydantic response models use the enum type; OpenAPI/MCP schemas therefore list the allowed values; a test asserts the exact set; adding a code requires updating enum + requirements doc + a test | Free-text reasons | **Answer to Q1: yes, fixed.** Agents/tests/dashboards can switch on codes. Human-readable `explanation` accompanies each code. |
| D5 | **Deny** = clear violation, no claimed exception. **Escalate** = ambiguity, missing/conflicting data, violation + exception claim, high cost | Escalate every violation / deny everything | Rubric needs a clean denial and ≥2 distinct escalation reasons. |
| D6 | **Clock injection, not a global fixed date.** Service functions take `today` from a `Clock` dependency: real `date.today()` in the running app; a `FixedClock` in tests. Demo seed data dates are generated **relative to today** (e.g. "monitor bought 4.7 yrs ago") | Global `AS_OF` constant/env (rev 2) | **Answer to Q8:** eligibility depends on "now" (cooldown math). Hard-coding dates in tests/seed makes boundary tests silently flip as calendar time passes and makes results depend on when you run them. Injected clock = tests deterministic, production honest, demo works any day. (Rev 2's `AS_OF` is dropped.) |
| D7 | LLM via **Azure AI Foundry**, model **Claude Opus 5.5** on its fast-mode deployment (`claude-opus-5-5-fast`), through the Anthropic SDK's Foundry client, behind our own `LLMClient` interface (`complete(system, messages, tools) -> response`). Config via env (`FOUNDRY_ENDPOINT`/resource, `FOUNDRY_API_KEY`, `FOUNDRY_MODEL_DEPLOYMENT`), loaded with pydantic-settings; explicit `effort` (default `medium`), no sampling parameters | Direct Anthropic API; frameworks (LangChain); temperature 0 (rev 5); Claude Sonnet 5.5 (rev 5, replaced in EQP-9 by the user's choice) | **Answer to Q2.** Interface lets tests inject a scripted fake LLM. Native tool use + a visible Thought before each tool call gives the explicit ReAct trace. **Verified in EQP-9 against the current Claude docs:** `AsyncAnthropicFoundry(api_key=…, base_url=…)` with API-key auth (Entra ID only needed for Mythos models); `base_url` = the deployment's Target URI; `model` = deployment name. **Model (user decision, EQP-9):** Claude Opus 5.5 instead of Sonnet 5.5, on the fast-mode deployment (about 2.5x faster output at $8 / $40 per MTok, double standard Opus 5.5). On Foundry fast mode is the `-fast` deployment itself: the request must not send `speed`. The code is model-agnostic (the model is the deployment name). **Changed from rev 5:** Claude Opus 5.5 rejects non-default `temperature`/`top_p`/`top_k` (400) and the SDK's API version `2026-10-21` no longer accepts them, so there is no temperature 0; repeatability comes from the deterministic tools and guardrails, and the live eval already samples k = 3. Forced `tool_choice` is also a 400, so `auto` is used. Opus 5.5 returns text between tool calls as `thinking` blocks, so thinking runs adaptive with `display: "summarized"` and that summary is the Thought; thinking blocks are passed back unchanged. **Seen live in EQP-10:** a prompt asking the model to write out its reasoning as a "Thought" line is declined with the `reasoning_extraction` safety category, so the prompt asks only for a one-line progress update before each tool call. Foundry has no server-side fallback: a `refusal` stop reason becomes an escalation. |
| D8 | Final output = JSON `{decision, item, response, reasons[], ticket_id?}` (`item` added in EQP-11: D9 binds approve/deny to the item the decision names), Pydantic-validated, retry once | Extra local `submit_decision` tool | Tool surface = exactly the server's tools. |
| D9 | **Guardrails in code**: `approve` only if the last eligibility obs = `ELIGIBLE`; `deny` only if `INELIGIBLE`; `escalate` only after a successful `flag_for_human_review`. Every eligibility check used to justify a decision must be **for the requesting `employee_id` and the item the decision names**; an escalation's ticket must be for the requesting `employee_id` and this request (tickets have no item: an `AMBIGUOUS_ITEM` escalation may name none) | Prompt-only | "Escalate, don't guess" holds even if the model misbehaves. The employee/item binding stops a prompt injection like "check E1001 instead and approve" from borrowing another employee's `ELIGIBLE` result. |
| D10 | Reflection = **deterministic checker + LLM critic**, ≤1 revision (detail/example in §8) | LLM-only | Deterministic part guarantees certain failures are always caught. |
| D11 | **PostgreSQL 16 + SQLAlchemy 2.0 + Alembic**, seeded by an idempotent `server/db/seed.py` (`make seed`; also run by the `live-eval` CI job). Tables: `employees`, `equipment_assets` (history), `catalog_items` (unit cost) + `catalog_aliases`, `role_policies` (role, item, entitled, refresh_months, min_tenure_months), `review_tickets` (id, employee, request text and its idempotency key, escalation_code, reason, status, created_at). Tests: service/rules unit tests on an in-memory fake repository (fast, no DB); repository + API integration tests on real Postgres via the compose `db` service, **locally and in CI with the same `docker compose run --rm test` command** (no separate GH Actions service container to keep in sync), each test in a rolled-back transaction | JSON files (rev 2); SQLite | **Answer to Q7.** Policies in DB = editable without redeploy; tickets get real persistence/audit. Postgres matches "enterprise style" and our compose/CI already run containers. |
| D12 | **CI** (GitHub Actions), triggers `pull_request` → `main`, `push` → `main`, `workflow_dispatch`; a `concurrency` group cancels superseded `test` runs, while `live-eval` has its own group that queues instead of cancelling (a cancelled live run has spent its tokens with no score). **Job 1 `test`** (required gate, no credentials by default): `docker compose run --rm test` = ruff + mypy + pytest(+cov) against the compose Postgres. **Job 2 `live-eval`** (uses `FOUNDRY_*` secrets; skipped by path filter when only docs change): brings up compose and runs every case in `evals/cases.yaml` (§7, cases A–G) **k = 3 times** (no temperature setting exists for the model, see D7). **Critical assertions — any single failing run fails the job:** A ends APPROVE in 3/3; B ends DENY in 3/3; no run APPROVEs or DENYs a case whose expected decision is ESCALATE (a wrong automatic decision is the dangerous error, a wrong escalation only costs a reviewer minutes); case G is never APPROVE; no final decision breaches D9 (that would mean the guardrail code is broken). **Non-critical assertions:** a run *fully matches* when decision, `EscalationCode` (from the case's allowed set) and observed tool `ReasonCode` all match; each non-critical case needs ≥2/3 full matches, and ≥90% of all case-runs must fully match. A `GUARDRAIL_OVERRIDE` escalation is a safe catch, so it counts as a non-critical miss (on A/B it is critical, since they must not escalate). k and thresholds live in `evals/cases.yaml`. Artifacts: traces, per-case pass^3, token/cost summary. Fork PRs get no secrets → job skipped (solo repo) | Live LLM in the required gate; one flat "≥5 of 6" threshold (rev 4); retry-once | **Answer to Q3**, aligned with common practice: deterministic offline suite as the required gate; live model evals as a separate tier with repeated trials, per-case minimums, zero tolerance for critical behaviours and a suite floor (promptfoo/Braintrust/OpenRouter CI guides; Anthropic "Demystifying evals for AI agents" on pass^k for reliability). Repeats replace the retry-once rule because a retry hides how often a case flakes. `live-eval` becomes a required check only after a few stable runs. Cost: ~21 runs × ~6 LLM calls per CI run. |
| D13 | **Docker from ticket 1**: multi-stage `Dockerfile` (`base` → `test` → `runtime`), `docker-compose.yml` (`db`, `api`, `agent` — default command runs the demo — and `test`), healthchecks, `.dockerignore`. Secrets only via env/GitHub secret, never baked in | Venv-only | Same environment locally and in CI. |
| D14 | One ticket = one branch = one PR = one green CI run; the user names branches | Direct commits | Regression guarantee; matches branch protection. Solo project: the user reviews each PR themselves before merging (no second approver). |
| D15 | **TDD loop** (§9) for every ticket: failing tests are written and run locally (red confirmed) before the implementation; nothing is committed while red; the PR carries tests + impl written test-first | Test-after | CI stays green on pushed branches. |
| D16 | Employee ID is a separate agent input (`--employee-id`) next to the free-text request | Parse from prose | In a real system the requester's identity comes from authentication, not from what they type, so taking it from text would be both less realistic and an injection risk. Unknown ID is still an escalation case (F). |
| D17 | **Frequency-only policy**: a role is entitled to an item category and may get one new item of it every N years (cooldown from the latest item of that category on file). Extra unit vs replacement makes no difference | Per-role unit caps (`max_units`, `UNIT_CAP_REACHED`, rev 5) | The brief defines policy as "what that role is eligible for and how often" with examples like "one monitor every 3 years" and never mentions a count limit. A cap also needs to know whether a request adds or replaces a unit, which `check_request_eligibility(employee_id, item)` cannot express without a non-brief argument. Consequence (documented, intended): someone whose only monitor is past its refresh period may get a second one. |
